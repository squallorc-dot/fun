## 不變原則

1. 保留 G01～G06、七英雄、五章、繁中／日文、OST、進度記錄、單人模式、所有動畫／畫質與四種操作配置。不改低品質模式，固定 120Hz 物理與既有低幀率公平性。
2. 第一輪只採用 **GitHub Pages + 原生 JavaScript + WebRTC**，不註冊外部服務、不租主機、不開通付費資源。即時雙人須明確啟用；不影響單人進度與 G06 五章錦標賽。
3. **不宣稱能自動建立房間、跨網穩定連線或正式防作弊排行榜。** GitHub Pages 不能跑常駐伺服器；WebRTC `iceServers: []` 不包含 STUN/TURN，中繼連線不可用。首輪同一 LAN 使用手動貼 offer／answer 交換包含 ICE 的 SDP；不同網路可能無法配對。
4. 雙人邀請／SDP 可能包含網路候選資訊或可連線位址：不得傳 Google Analytics、伺服器、URL query、本地永久紀錄或錯誤記錄；UI 應提醒只分享給可信朋友。分享挑戰 code 與 SDP 嚴格分離。

## 6A-0：先行 P2P 傳輸原型

**可立即實作的純前端能力：**
- `RTCPeerConnection({iceServers: []})` 手動 offer／answer，等待 ICE gathering complete 後才輸出描述；輸入做 JSON version/type/size/sdp 檢查，不允許 HTML 插入。
- Reliable control channel 保證有序訊息；選用獨立低延遲 input channel `{ordered:false,maxRetransmits:0}`，並有封包序列驗證、緩衝上限與最新完整輸入重送。
- 觀察 `connectionState`、`iceConnectionState`、datachannel onopen/onclose；避免頁面離開或背景節流時無限更新。
- 驗證可在兩台不同實體裝置操控遠端測試輸入，測 RTT 分位數／定時 ping、輸入收送計數與連線失敗。**只完成傳輸層不能標示 G05 真正雙人遊戲已完成。**

## 遊戲同步設計（6A-1 以後）

房主為唯一權威，120Hz 固定物理；客端不執行獨立勝負判定。輸入封包 `{v,seq,tick,axis,actions}` 白名單、有界大小與頻率；權威快照 `{v,tick,entityState,score,phase,checksum}` 週期傳輸；得分／發球／倒數／勝負採可靠有序傳輸，避免重複結算，輸入軸採低延遲通道防阻塞。無法接收到新輸入時回到中性操作，**不能把最後按住的攻擊／加速永久延續**。

預測、插值與回滾如需加入，應局部修改，不降低場景／角色／特效精度；模擬時鐘與每秒實際渲染畫格分離。不相容協定版本直接拒絕，不猜測或信任遠端自報分數。

**風險：** 房主仍可操控自己的執行環境，這不是具備獨立第三方裁判的競賽；不同網路受 NAT、ICE、mDNS、防火牆限制；手機背景可能強制中斷 WebRTC 與音訊。

## 必須保留的驗收

每次提交都跑 `verify`、`browser`、`arcade-engines`、`arcade-session-browser`、`arcade-controls-browser`、`arcade-performance-browser` 六項 GitHub CI，絕不刪舊斷言；保留 G02 裝置公平 5,355 檢查、G06 5C 競速矩陣／平衡門檻、七英雄 2x 圖集、OST 與 G05 既有桌球視角。新測試加入兩個獨立瀏覽器 peer 的真實 ICE／RTCDataChannel 訊息；進階對戰須測權威碰撞／得分、存檔隔離、拒絕不合法封包、20Hz／120Hz 時脈及 10～240 FPS、一局完整遊戲及重試。

網路品質分開提供 **受控模擬**（0／50／100／150／200ms RTT、抖動、0／1／3／5% 遺失）與 **兩台真機 LAN** 結果；自動化 Chromium 成功不等於實體 iPhone／Android／Windows Chrome／Edge。RTT p50/p95、jitter、掉包、校正／FPS、比分不一致、連接率為必要數據。LAN 理想 RTT <50ms，但不是保證。原 `Image.decode()` 偶發錯誤持續追蹤。
